### ⚠️ 经验教训

**Session 清零两步走（无需重启）**：
1. **清磁盘** — 清空/truncate `.jsonl` transcript 文件
2. **清状态** — 重置 `sessions.json` 中的 `systemSent=false`、`totalTokens=0`

**不需要重启 gateway！** OpenClaw 从 `sessions.json` 重新加载状态，清完直接生效。之前误以为需要重启，实际上是 API proxy 的 thinking 参数问题（独立 bug）被错误归因到了 session 内存状态。

**Lock 文件可能残留** — session 异常中断时 `.lock` 文件可能不会被清理，导致后续请求超时报 `session file locked`。手动删除即可。

**子任务 0 tokens = 从未启动** — 如果 spawn 的子任务 `totalTokens=0`，说明它在初始化时就失败了（通常是 API 错误），应立即标记 failed 而不是等超时。

**INVALID_ARGUMENT ≠ context 太大** — 这个错误也可能出现在 context 正常但内容有问题的情况下。排查时先用 curl 直接测 API 确认 proxy 是否正常。

## 🔧 今日修复经验总结（06:30-09:10 SGT）

### 1. 主对话卡死不响应（t013 排查）
- **现象**：Luna 在群聊里完全不回消息，只能手动重启
- **根因**：01:16 SGT 一个 agent embedded run 超时（10min timeout），之后 main lane 阻塞，所有消息入队但永远不消费
- **看门狗失效**：watchdog 检测到了问题（心跳停 2628 分钟），但 Python f-string 语法 bug 导致每次执行到重启逻辑就 crash：`{hb_minutes:.0f if hb_minutes else '?'}` — 三元表达式不能放在 format spec 里
- **修复**：修了 watchdog Python bug
- **教训**：看门狗的报警/恢复路径必须有测试覆盖，否则关键时刻会失效

### 2. 子任务 announce 串台
- **现象**：子任务完成后的通知消息发到了错误的群聊
- **根因（层1）**：`sessions_spawn` 的 announce 走 main session 的 deliveryContext，绑定到最后活跃的群
- **修复**：`patches/fix-announce-no-reply.py` — 检测子任务最终回复为 NO_REPLY 时跳过 announce
- **根因（层2）**：修了 announce 后发现串台仍存在。原因是 step-done 触发 `cron wake now` → 心跳处理 advance → 心跳 LLM 的回复走 deliveryContext → 又串台了
- **修复**：`planner.py` 的 step-done 改为直接用 `openclaw cron add --message --no-deliver` spawn 隔离任务，完全绕过心跳 LLM
- **教训**：串台有多层原因，修一层可能暴露下一层。消息路由问题要追到底

### 3. 任务从未实际 spawn（僵尸任务）
- **现象**：任务在 task-board 里标记 running（19分钟），但 session_key 为空，实际从未启动
- **根因**：planner step-done 创建了任务（task-manager add + start），但 `schedule_advance` 只写了 pending 文件等心跳来 spawn。心跳 LLM 没有正确处理 check-advances 的 spawn_prompt
- **修复1**：`_spawn_via_cron()` — step-done 直接通过 cron agentTurn 在隔离 session 里 spawn 下一步
- **修复2**：`task-health-check.py` 增加僵尸检测 — session_key 为空 + 运行超 2 分钟 → 自动标记失败
- **教训**：任何异步操作都要有"确认启动"的检测机制，不能只看状态标记

## 🔒 群聊隐私判断修正（18:50 SGT）

### 问题
知识同步系统的隐私拦截误判了双人群（Carl + Bot）。

**误判场景**：
- `oc_680d9c843e6a0ad501de9299a97f3a7e` 是 Carl + Luna 的双人群
- 但代码简单判断 `kind == "group"` 就视为多人群，导致拦截
- 结果：知识同步对真正的私聊也失效了

### 根因
OpenClaw 的 `kind: group` 只表示"不是 DM"，不代表"有多人"。
Lark 的群聊可以是：
- 双人群（Carl + Bot）→ 实际上私聊
- 多人群（Carl + Bot + 其他人）→ 真正的群聊

### 修复
**新增真正的群成员检查** (`knowledge-sync.py`)：
```python
def check_group_privacy_cached(chat_id):
    # 调用 Lark API 获取群成员
    # 过滤掉 Bot 自己
    # 如果只剩 Carl → 视为私聊
    # 如果有其他人 → 视为多人群
```

**缓存机制**：
- TTL 1 小时，避免频繁 API 调用
- 缓存 key: chat_id → {is_private, expires}

**新的判断逻辑**：
```
private 文件 + 双人群 (Carl+Bot) → ✅ 发送
private 文件 + 多人群 (有其他人) → ❌ 拦截
```
