# Token 用量优化策略研究

> 研究日期：2026-02-08  
> 目标：探索在 OpenClaw / Luna 场景下降低 LLM token 消耗的可行技术路径  
> 状态：内部参考文档

---

## 一、问题背景

在 OpenClaw 这类「长驻式 AI 助手」架构中，token 消耗具有几个显著特征：

1. **持续性消耗**：心跳轮询、定时任务、群聊监听等均会产生持续的 token 消耗
2. **上下文膨胀**：多轮对话、工具调用结果、文件读取内容等迅速填满上下文窗口
3. **重复性高**：系统提示（SOUL.md、AGENTS.md 等）在每个 session 中重复注入
4. **子任务开销**：每个 subagent 都携带完整的系统上下文，独立消耗 token

根据 JetBrains 在 NeurIPS 2025 的研究，AI agent 的上下文增长速度远超其有效利用能力——上下文变大后，很快就从「有用信息」退化为「噪声」，但成本却线性增长。这意味着我们在 token 上的投入存在大量浪费空间。

## 二、上下文压缩技术

### 2.1 Prompt 压缩工具

#### LLMLingua 系列（Microsoft Research）

LLMLingua 是目前最成熟的 prompt 压缩方案，已发展到三代：

- **LLMLingua**（EMNLP 2023）：基于小模型（如 LLaMA-7B）的困惑度（PPL）进行 token 级压缩，包含三个模块——预算控制器、迭代 token 级压缩、分布对齐。可达 **20x 压缩比**，性能损失最小。
- **LongLLMLingua**（ACL 2024）：针对长文档场景优化，在 4x 压缩下反而 **提升 17.1% 性能**，因为去除了干扰信息。
- **LLMLingua-2**：通过 GPT-4 数据蒸馏训练的轻量 token 分类器，更快更稳定。

**适用场景**：
- 长文档/文件内容注入到 prompt 时
- RAG 检索结果在送入 LLM 前的预处理
- 工具调用返回的大量文本结果

**限制**：
- 需要运行一个小型语言模型（推理开销）
- 对结构化数据（JSON、代码）压缩效果不如自然语言
- 压缩后的文本人类不可读，调试困难

#### Selective Context

更轻量的方案，通过自信息（self-information）评估每个 token 的信息量，移除低信息量的 token。不需要训练，直接使用预训练模型的 logits。

**与 LLMLingua 对比**：实现更简单，但压缩比和保真度不如 LLMLingua-2。

### 2.2 对话历史管理策略

JetBrains Research（2025）系统对比了两种主流方案：

#### 方案 A：LLM 摘要（LLM Summarization）

将历史对话用另一个 LLM 调用压缩为摘要，这是 OpenHands、Cursor、Warp 等产品采用的方案。

**工作流程**：
1. 对话历史超过阈值时触发
2. 用一个（通常更小的）模型对历史进行摘要
3. 摘要替代原始历史，与新消息一起送入模型

**优点**：
- 理论上支持无限轮对话（反复压缩）
- 保留语义完整性
- 压缩比高（可将数万 token 压缩到几百）

**缺点**：
- 摘要本身消耗额外 token
- 可能丢失关键细节
- 需要一次额外的 LLM 调用（延迟 + 成本）

#### 方案 B：观察掩码（Observation Masking）

仅隐藏工具调用返回的观察结果（observation），保留推理和动作历史。

**原理**：Agent 的每个轮次包含三部分——推理（reasoning）、动作（action）、观察（observation）。观察部分（如文件内容、命令输出）通常占据 80%+ 的 token，但其信息在后续轮次中迅速衰减。掩码将老的观察替换为占位符（如 `[OBSERVATION HIDDEN]`）。

**优点**：
- 实现简单，无需额外 LLM 调用
- 保留完整的推理链条
- 成本为零（纯裁剪操作）

**缺点**：
- 上下文仍会线性增长（只是更慢）
- 可能丢失需要回溯的观察信息

#### 推荐：混合方案

JetBrains 的实验表明，最佳方案是 **观察掩码 + 定期 LLM 摘要** 的混合策略：
- 近期轮次：保留完整信息
- 中期轮次：掩码观察，保留推理和动作
- 远期轮次：压缩为摘要

这与 OpenClaw 已有的 **compaction** 机制理念一致。

### 2.3 RAG vs 全量上下文

2025 年的研究（arXiv: 2501.01880）系统对比了 RAG 与长上下文直接输入：

| 维度 | RAG | 全量上下文 |
|------|-----|----------|
| Token 消耗 | 低（仅检索相关片段） | 高（全文注入） |
| 准确性 | 依赖检索质量 | 通常更高（信息完整） |
| 适用场景 | 大规模知识库、FAQ | 单文档深度理解 |
| 延迟 | 检索 + 推理 | 纯推理（但更长） |
| 成本 | 检索基础设施 + 较少 token | 更多 token |

**关键发现**：
- 对于对话型和一般问答任务，RAG 有优势
- 对于需要文档全局理解的任务，长上下文更优
- 现代 RAG 的设计哲学是 **「强检索 + 精推理」协调有限上下文窗口**

**OpenClaw 场景建议**：
- 记忆文件（MEMORY.md、daily notes）适合 RAG 化——按需检索而非全量注入
- 系统提示（SOUL.md、AGENTS.md）适合直接注入（结构稳定、prompt caching 友好）
- 工具结果适合即用即弃——用完掩码

## 三、缓存策略

### 3.1 Prompt Caching（API 原生支持）

**Anthropic Claude**：
- 使用 `cache_control` 指令标记可缓存的 prompt 前缀
- 最小缓存阈值：Claude 3.5/3.7 Sonnet 为 1024 tokens，Haiku 4.5 为 4096 tokens
- 缓存命中时 **降低 90% 输入 token 成本**
- TTL（存活时间）：5 分钟（每次命中刷新）
- 最多 4 个缓存断点

**OpenAI**：
- 自动缓存——无需任何代码修改
- 前缀匹配：相同前缀的请求自动享受缓存折扣
- 缓存 token 成本为 **正常价格的 50%**
- 最小前缀长度：1024 tokens

**Google Gemini**：
- Context Caching API，支持显式创建缓存对象
- 可设置自定义 TTL
- 适合固定系统提示 + 变化用户输入的场景

**核心原则**：
1. **将稳定内容放在 prompt 前部**——系统提示、指令、示例等不变内容前置
2. **变化内容放在后部**——用户消息、动态上下文放在末尾
3. **保持前缀一致性**——即使微小的前缀变化也会导致缓存失效
4. **合理设计缓存断点**——在 system prompt 结束处、tools 定义结束处等位置设置

**对 OpenClaw 的意义**：
OpenClaw 的 system prompt 非常长（AGENTS.md + SOUL.md + TOOLS.md + runtime context + workspace files），这部分内容在同一会话内高度稳定。如果 API 提供商支持 prompt caching，这部分天然适合缓存，可节省大量输入 token 成本。

### 3.2 语义缓存（Semantic Caching）

传统的精确匹配缓存在 LLM 场景下命中率极低，因为自然语言的表达方式高度多样化。语义缓存通过 embedding 相似度匹配，在 **意图层面** 而非 **文本层面** 进行缓存。

**工作流程**：
1. 将用户 prompt 转为向量 embedding
2. 在向量数据库中搜索相似的历史 prompt
3. 如果相似度超过阈值，直接返回缓存的响应
4. 否则调用 LLM，将新的问答对存入缓存

**主流工具**：
- **GPTCache**（Zilliz）：与 LangChain、LlamaIndex 集成，支持多种相似度后端
- **TrueFoundry AI Gateway**：内置语义缓存层
- **ScyllaDB + 向量搜索**：低延迟语义缓存实现

**两级缓存架构**（推荐）：
- 第一级：精确匹配（接近零成本，捕获完全重复的查询）
- 第二级：语义匹配（embedding 计算 + 向量搜索，仍远低于 LLM 调用成本）

**适用性分析**：
- ✅ 高度适用：FAQ、知识问答、重复性操作指导
- ⚠️ 部分适用：带上下文的对话（需要连上下文一起缓存）
- ❌ 不适用：个性化创作、需要最新信息的查询

**OpenClaw 场景**：语义缓存对于心跳任务中的重复检查（天气、日程等）有潜在价值，但需注意缓存新鲜度——过期的缓存比不缓存更危险。

### 3.3 工具结果缓存

对于 OpenClaw 中频繁调用的工具（文件读取、web 搜索等），可以在应用层缓存结果：

- **文件内容缓存**：同一文件在短时间内多次读取时，缓存内容并检查文件修改时间
- **搜索结果缓存**：相同或相似搜索词的结果可缓存一定时间
- **API 调用缓存**：日历、邮件等 API 的结果可设置合理的 TTL

## 四、模型路由优化

### 4.1 核心思想

并非所有请求都需要最强（最贵）的模型。ICLR 2025 发表的 RouteLLM 研究表明：

- 合理路由可以在 **仅使用 26% 的强模型调用** 的情况下，保持 **95% 的强模型质量**
- 在 MT-Bench 上可实现 **85% 的成本削减**

### 4.2 路由策略

#### 规则路由（Rule-Based）

最简单的方案——根据任务类型预设路由规则：

| 任务类型 | 推荐模型层级 | 示例 |
|---------|------------|------|
| 格式化、分类、提取 | 超廉价模型（nano 级） | 文本分类、JSON 格式化 |
| 摘要、翻译、简单问答 | 中等模型（mini 级） | 新闻摘要、日常对话 |
| 复杂推理、编程、创作 | 强模型（opus/pro 级） | 代码审查、架构设计 |

**优点**：零开销、可预测  
**缺点**：需要手动分类，无法处理边界情况

#### 机器学习路由（ML-Based，如 RouteLLM）

使用训练好的分类器自动判断请求复杂度：

- **矩阵分解路由器**：学习模型-查询对的评分函数（效果最佳）
- **BERT 分类器**：微调 BERT 预测最优模型
- **embedding 相似度路由器**：基于与训练样本的相似度路由

#### LLM 路由（LLM-Based）

用一个小型 LLM（如 Qwen 1.75B）对请求进行复杂度分类后再路由。NVIDIA 的 LLM Router Blueprint 采用此方案。

**权衡**：路由器本身的推理开销 vs 节省的大模型开销。对于高频场景，ML-Based 路由器（11µs 开销）比 LLM-Based 路由器更高效。

### 4.3 OpenClaw 场景的路由建议

| 场景 | 推荐模型 | 理由 |
|------|---------|------|
| 心跳检查 | 小模型（haiku/mini） | 逻辑简单，主要是条件判断 |
| 日常对话 | 中等模型（sonnet/gpt-4o） | 平衡质量与成本 |
| 子任务研究 | 可调——简单收集用小模型，深度分析用大模型 | 按任务复杂度路由 |
| 群聊参与 | 小模型（判断是否需要回复）→ 必要时升级 | 两步路由节省大量 token |
| 代码编写/调试 | 强模型 | 代码质量对准确性要求高 |

## 五、OpenClaw 场景下的具体优化建议

### 5.1 心跳任务优化

当前心跳任务每次都会注入完整的系统上下文 + HEARTBEAT.md + 近期记忆文件。优化方向：

1. **精简 HEARTBEAT.md**：保持最小化，仅列出必要的检查项和状态，避免冗长描述
2. **状态驱动的心跳**：在 `heartbeat-state.json` 中记录上次检查时间，只在到期时才执行检查，否则直接返回 HEARTBEAT_OK
3. **用小模型处理心跳**：心跳逻辑通常简单（检查邮件？检查日历？没有就跳过），用 haiku 级模型足矣
4. **减少心跳频率**：将心跳间隔从默认值适当延长，配合 cron 任务处理精确定时需求

**预估节省**：心跳任务可能占总 token 消耗的 30-50%（高频 + 重复系统提示），优化后可减少 60-80%。

### 5.2 子任务 Prompt 模板优化

当前每个 subagent 都携带完整的 AGENTS.md、TOOLS.md 等上下文。优化方向：

1. **精简子任务上下文**：子任务不需要 MEMORY.md、完整的 AGENTS.md 群聊指南等。可以为 subagent 设计精简版系统提示
2. **任务特定注入**：只注入与任务相关的工具说明和上下文文件
3. **模板变量化**：将子任务的固定指令（"完成后更新 backlog"、"不要用 message 工具"）提取为模板变量，避免每次在任务描述中重复
4. **批量子任务**：将多个相关的小任务合并为一个子任务，减少 N 次系统提示注入

### 5.3 Compaction 策略调优

OpenClaw 已有 compaction 机制（对话历史压缩），可进一步优化：

1. **分层压缩**：
   - 最近 3-5 轮：保留完整
   - 5-20 轮前：掩码工具输出，保留推理和动作
   - 20 轮前：压缩为摘要

2. **触发阈值调优**：
   - 当前 token 用量达到上下文窗口的 60% 时触发 compaction（而非等到 80%）
   - 更早触发 = 更低的峰值消耗

3. **摘要质量保障**：
   - 用结构化格式（而非自由文本）存储摘要
   - 关键信息显式保留：用户偏好、待完成任务、已做决策
   - 定期验证摘要是否丢失关键信息

### 5.4 系统提示瘦身

当前 OpenClaw 的系统提示（运行时注入）体量较大。优化方向：

1. **按需加载**：不是每个 session 都需要所有 workspace files。可根据任务类型选择性注入
2. **层级化提示**：核心规则（安全、身份）必须每次注入，操作指南（心跳行为、格式化规则）可按需注入
3. **压缩静态内容**：AGENTS.md 中的很多内容可以精简表述（如群聊指南可压缩 50%+）
4. **利用 prompt caching**：确保系统提示始终在 prompt 最前部，最大化缓存命中率

### 5.5 综合节省估算

| 优化措施 | 预估 Token 节省 | 实施难度 | 优先级 |
|---------|---------------|---------|-------|
| 心跳用小模型 | 40-60% 心跳成本 | 低 | ⭐⭐⭐ |
| Prompt caching 优化 | 50-90% 缓存命中部分 | 低 | ⭐⭐⭐ |
| 精简心跳上下文 | 20-30% 心跳成本 | 低 | ⭐⭐⭐ |
| 子任务 prompt 精简 | 30-50% 子任务成本 | 中 | ⭐⭐ |
| Compaction 策略调优 | 20-40% 长对话成本 | 中 | ⭐⭐ |
| 系统提示瘦身 | 10-20% 全局成本 | 中 | ⭐⭐ |
| 模型路由 | 30-85% 路由覆盖部分 | 高 | ⭐ |
| 语义缓存 | 10-30% 重复查询 | 高 | ⭐ |

## 六、实施路线图

### 短期（1-2 周，低悬果实）

1. **精简 HEARTBEAT.md** 和心跳逻辑
2. **调整系统提示结构** 以最大化 prompt caching
3. **审查 AGENTS.md / TOOLS.md** 精简冗余内容

### 中期（1-2 月）

4. **实现子任务 prompt 模板分级**——按任务类型注入不同级别的上下文
5. **调优 compaction 参数**——阈值、摘要格式、保留策略
6. **探索心跳任务使用 smaller model** 的可行性

### 长期（探索性）

7. **评估 RouteLLM 风格的模型路由** 在 OpenClaw 中的集成可能
8. **试点语义缓存** 用于高频重复查询场景
9. **探索 LLMLingua 类压缩** 用于长文件内容注入
