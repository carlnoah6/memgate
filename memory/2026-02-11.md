### 23:18 SGT (Feb 12) — 知识同步总线测试通过 ✅

**端到端验证完成**：在 TOOLS.md 写入"Carl 最喜欢夏威夷披萨"→ 广播到所有 session → Carl 在另一个 Lark 群问 Luna → 成功回答。

**开发过程中修复的 3 个 bug**：

1. **inotifywait 监听目标错误**
   - 问题：监听单个文件路径，编辑器写文件时 unlink+create 不触发 modify 事件
   - 修复：改为监听目录 + close_write,moved_to 事件
   - 教训：inotifywait 监听单文件有陷阱，很多编辑器（vim/nano/Python write）用原子写入（写临时文件→rename），不触发原文件的 modify 事件

2. **lark-send-message.sh 参数错位导致无限挂死**
   - 问题：脚本设计 `$1=chat_id, $2=MODE, $3=MESSAGE`，但调用方式是 `script <chat_id> "消息"`（只传 2 个参数）
   - 结果：消息文本被当成 MODE 参数，MESSAGE 为空 → `cat` 等 stdin → 无限挂住
   - 修复：增加判断——如果 $2 不是 --post/-/--post-json，就把它当成消息文本
   - 教训：shell 脚本参数设计要考虑最常见调用方式，必须做 fallback 处理。另外 urllib.request.urlopen 必须加 timeout

3. **broadcast 阻塞 watcher 主循环**
   - 问题：watcher 检测到变更后同步调用 broadcast（subprocess.run），broadcast 需要连接多个 session（每个几秒），总耗时 > debounce 时间，导致后续变更漏检
   - 修复：改为 subprocess.Popen 异步执行，watcher 立即返回继续监听
   - 教训：事件驱动系统中，事件处理必须异步，不能阻塞主循环

**架构经验**：
- `openclaw agent --session-id` 是绕过 LLM 直接注入 session 上下文的唯一方式
- 注入 ≠ 发消息给用户：注入只更新 LLM 上下文，不会自动显示在聊天里
- 通知必须包含**实际变更内容**（diff），不能只说"文件变了"——session 无法自行重新读文件
- 重启后 watcher 必须自动恢复 → 写在 check-restart.sh 里（代码保证），不写在 HEARTBEAT.md 里（LLM 自觉）

**核心认知：**

3. **事件处理必须异步**：事件驱动系统的 handler 不能阻塞主循环
4. **shell 脚本参数必须有 fallback**：`$2` 是位置参数，不同调用方式会导致含义不同
5. **urllib.request.urlopen 没有默认 timeout**：在网络不稳定时会无限挂住，必须显式设置

### 规划器（planner.py）使用问题复盘（2/12 代码 review 时总结）

**问题 1：replan 时 title/prompt 不被识别 → desc fallback "Step N"**
- **现象**：init 创建的步骤 desc 全是 "Step 1", "Step 2" 等，实际 title 被忽略
- **根因**：`cmd_init` 里用 `s.get("desc", f"Step {i}")`，不检查 `title` key；而 `cmd_replan` 用 `raw.get("title", raw.get("desc", ...))`，两者行为不一致
- **修复**：抽出 `normalize_step()` 函数统一映射 title>desc>fallback 和 prompt>detail>""，init 和 replan 都调用同一个函数
- **教训**：多个入口写同一种数据时，必须共用映射逻辑，不能各写各的

**问题 2：step-done 后 auto-advance 创建任务但不 spawn**
- **现象**：step-done 自动推进了下一步（创建了 task、标记 running），但没人 spawn 子任务去执行
- **根因**：schedule_advance 尝试用 openclaw cron 调度唤醒，但 cron 不可用（返回非 0），fallback 写了 pending 文件，但 pending 文件只在心跳的 check-advances 时被检查，心跳间隔 ~30min
- **结论**：这是架构设计的已知限制。step-done 的输出包含 `spawn_prompt`，**调用方（主 session 或子任务本身）应该看到输出并立即 spawn**。pending 文件是最后的安全网。
- **教训**：schedule_advance 的 cron→pending fallback 链路是 best-effort，不能依赖它立即工作

**问题 3：子任务搞混 task_id（t008 vs t009）**
- **现象**：子任务回调时用错了 task_id，导致状态混乱
- **根因**：因为 desc 全是 "Step N"，子任务看不出自己对应哪个步骤，只能靠 task_id 区分，容易搞混
- **修复**：normalize_step 修复后，desc 有有意义的描述，子任务更容易对应
- **教训**：无意义的默认值（"Step N"）会导致下游混淆

**问题 4：check-advances 在 pending 文件路径中不检查 has_running**
- **现象**：有 running 步骤但 pending 文件存在时，check-advances 误报需要推进
- **根因**：主循环正确检查了 has_running，但处理 pending 文件的分支忘了检查
- **修复**：在 pending 文件处理路径中增加 `has_running` 检查

**所有问题的共同根因**：
代码写于匆忙的首次实现（2/11），init 和 replan 的 key 映射不一致、边界检查不完整。
核心教训：**新功能上线后需要 code review**，特别是多入口写同一种数据的场景。
