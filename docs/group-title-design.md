## 核心设计原则

### 1. 话题跟踪 > 任务跟踪

**问题**: 最初设计基于 task-board.json 的 running 任务，导致：
- 子任务频繁变更 → 标题反复跳动
- 所有群显示同样任务 → 缺乏个性化
- 无任务时显示"空闲" → 忽略活跃对话

**解决方案**: 基于**话题**而非**任务**
- 3小时时间窗口内活跃对话 = 同一话题
- 自然冷却（几小时/一天没聊）= 话题结束
- 跨群聊同一件事 → 各自显示相关话题

### 2. 三层优先级

```
优先级1: 活跃规划器 → "🔄 <规划器名字>"
优先级2: 活跃对话   → "💬 聊<话题>"  
优先级3: 空闲       → "🌙 空闲"
```

**关键决策**: 规划器名字而非具体任务
- ❌ 不显示: "tid-0212-23 Step 3: API权限检查"
- ✅ 显示: "群标题自动更新"（规划器 goal）

### 3. 时间窗口设定

| 参数 | 值 | 理由 |
|------|-----|------|
| 活跃窗口 | 3小时 | 正常对话节奏，允许中断休息 |
| 冷却时间 | 6小时 | 区分"暂停"vs"结束话题" |
| 标题最大长度 | 15字符 | 手机端显示完整，不截断 |

## 经验教训

### ✅ 做得好的
1. **快速迭代**: 从任务跟踪→话题跟踪，3轮内找到正确方向
2. **用户驱动**: 根据 Carl 反馈实时调整，不固守最初设计
3. **配置化**: 关键词映射外置到 JSON，便于调整

### ⚠️ 踩过的坑
1. **过度工程**: 最初想显示完整任务描述 → 太长看不懂
2. **路径混乱**: chat_id 格式不一致（oc_xxx vs 后8位）
3. **函数缺失**: 重构时漏了 `get_session_file` 等辅助函数

### 🐛 Bug 修复记录（2026-02-12）
| Bug | 症状 | 根因 | 修复 |
|-----|------|------|------|
| `WORKSPACE` 未定义 | `NameError: name 'WORKSPACE' is not defined` | 常量定义在使用之后，导致运行时错误 | 调整代码顺序，常量定义放在文件顶部 |
| Chat ID 提取错误 | `get_active_planner_goal()` 总是返回 `None`，规划器检测失效 | 代码用 `[:8]` 取前8位，但实际文件名使用后8位（如 `a97f3a7e.json`） | 改为 `[-8:]` 取后8位 |

**关键教训**:
- 文件名/ID 匹配必须**实际验证**，不能假设格式
- 代码写完后要用真实数据跑 `--analyze` 测试
- 重构时注意变量定义顺序，Python 是解释执行

### 📝 核心洞察
- **用户视角**: Carl 要的是"一眼知道在聊啥"，不是"精确追踪每个子任务"
- **时间 > 状态**: 对话的自然节奏比系统状态更能反映"当前在做什么"
- **简洁至上**: 15字符内表达完整意图，宁可模糊也不要冗长

## 成长记录

### 从这次迭代中学到的

**1. 测试即真理**
- 没跑 `--analyze` 测试前，以为代码是对的
- 实际跑起来才发现两个低级 bug
- **固化**: 任何脚本修改后，必须先用 `--analyze` 验证

**2. 文件名是契约**
- `planner.py` 用 chat_id 后8位命名文件
- 其他代码必须遵循同一约定
- **固化**: 文档中明确记录命名规则，代码注释引用

**3. 重构是风险**
- 调整代码结构时容易漏掉依赖关系
- Python 的解释特性让这类错误只能在运行时暴露
- **固化**: 重构后必须完整测试所有路径

**4. 用户是最好的测试**
- Carl 问"有哪个群触发过规则"才暴露问题
- 自动化测试覆盖不了真实场景
- **固化**: 功能上线后主动验证，不要等用户发现
